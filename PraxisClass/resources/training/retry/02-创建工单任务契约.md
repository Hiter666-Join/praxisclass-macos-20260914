# 创建工单任务契约

材料编号：RETRY-CONTRACT｜版本：1.0  
AI辅助编制的教学业务约定，不是真实服务接口。

## 任务与参数

为“创建一张工单”设计重试处理：防止同一意图重复创建，并允许用户明确发起另一项相同内容的新操作。接口写作POST /training/tickets，仅用于阅读和仿真，不要求向此路径发真实请求。

教学调用者固定U-DEMO；它是情形身份，不是平台登录身份。原操作标识R-001，新操作标识R-002；发送序号独立递增，不代替操作标识。

P-01为本轮默认参数：

```json
{
  "title": "实训机无法连接课程服务",
  "description": "启动后连接失败，请协助排查"
}
```

概念请求包含caller、operationId与payload，不指定它们在真实HTTP协议中的鉴权或传输位置：

```json
{
  "caller": "U-DEMO",
  "operationId": "R-001",
  "payload": {
    "title": "实训机无法连接课程服务",
    "description": "启动后连接失败，请协助排查"
  }
}
```

## 两种服务端规则

| 模式 | 请求到达后的处理 |
|---|---|
| 未去重 | 每次到达都创建新工单，不识别此前的operationId |
| 按标识去重 | 先按caller＋operationId查记录；没有记录时创建工单，原子地保存参数和结果；已有记录且参数一致时关联原工单 |
| 去重模式中的参数冲突 | 已有同键，但title或description不同，返回冲突；不创建、不修改原工单，也不覆盖原操作记录 |

参数不参与组成判重键。第一张工单编号T-101，之后按T-102、T-103递增。成功响应携带关联工单编号；首次成功和重放均显示“成功”，不凭客户端响应额外声称服务器进行了哪种内部操作。冲突响应没有新工单编号。本课不扩展具体HTTP状态码契约。

重试仍表达原意图，正确做法保持原标识。新操作另用新标识，即使P-01不变。错误策略“每次重试都生成新标识”按R-002、R-003递增，意图仍记作重试，不能因发出的标识变了就改称合法新需求。

## 保障范围

一轮记录持续有效，事件串行推进，去重记录只抽象为未记录／已完成，创建与记账视为一个原子事件。本课不模拟并发处理中状态、服务重启、记录过期、业务失败恢复或跨服务事务；这套模型不构成永久或全局只执行一次的证明。

每个情形、每次切换服务端规则或重置都重新初始化空状态。V3的第一张工单也由本轮的正常事件创建。旧轮次和已提交成果不可随新策略回算。

## 观察与验证

必须验证V1、V2、V3。V1与V2首先都只给出客户端超时，学生可先判断再展开教学观察；V3给出正常成功后用户明确新建的需求。展开观察不设置答对门槛，但要注明判断发生时是否已看过全景或获得关键帮助。

客户端只显示实际发出次数、收到的响应与编号；服务端总数属于教学观察。客户端“收到编号序列”按收到次序保留重复项，同一个T-101收到两次仍记录两次；该序列长度不是服务器工单数。
