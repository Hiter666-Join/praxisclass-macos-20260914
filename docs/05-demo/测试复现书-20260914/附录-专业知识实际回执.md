**Q1 Content-Type 与 Accept**
- Content-Type 说明所附表示（请求体或响应体）的实际媒体类型，是“我发送的内容是什么类型”。依据：`KP-HTTP` KP-003。适用边界：它不是希望收到的响应类型；仅写 application/json 不会把任意文本变成合法 JSON。
- Accept 表达客户端可接受的响应媒体类型，可带偏好权重，是“我希望收到什么类型”。依据：`KP-HTTP` KP-004。适用边界：它不声明请求体类型，也不保证服务器一定按该格式返回。

**Q8：bisect_left 返回整数，为什么还不能直接认定找到了目标？**

- bisect_left 返回的是保持有序的“左侧插入位置”，相等元素存在时它是最左的那个位置（KP-036）。这个整数在“目标存在”和“目标不存在”两种情况下都有值：空列表返回 0，目标比所有元素都大返回长度，所以返回值本身不携带“找到／没找到”的含义（KP-036 适用边界）。

- 位置上的值等于目标，只支持“该位置匹配”；不存在时插入位置与本题约定的 -1 含义不同，两者不能混用（CODE-TECH「返回一个位置，还需要问什么」）。另外契约要求返回整数下标，不能用布尔值代替，也不能把 True 当 1（CODE-CONTRACT 函数约定）。
- 前提边界：bisect 类方法假定输入有序、不负责排序；本任务已约定非递减整数输入，不应把“处理无序输入”新增为必做项（KP-035）。同时，少量检查成立也不能宣称所有输入正确或已完成复杂度分析（CODE-TECH）。
